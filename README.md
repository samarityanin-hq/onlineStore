# Онлайн магазин

REST API интернет-магазина, разработанное на **Java** с использованием **Spring Boot**. Проект реализует JWT-аутентификацию (access + refresh токены с ротацией и отзывом через Redis), rate limiting, управление товарами, категориями и заказами (включая автоматическую отмену по таймауту), кэширование каталога через Redis, а также предоставляет REST API для взаимодействия с клиентскими приложениями.

## Архитектура проекта

Проект построен с использованием многослойной архитектуры.

```text
Client
   │
REST Controller
   │
Service ──── Redis (кэш каталога, refresh-токены, rate limiting)
   │
Repository
   │
PostgreSQL (миграции — Liquibase)
```

Основные слои:

* **Controller** — обработка HTTP-запросов;
* **Service** — бизнес-логика;
* **Repository** — взаимодействие с базой данных;
* **Entity** — модели базы данных;
* **DTO** — объекты передачи данных между клиентом и сервером;
* **Security** — JWT-аутентификация, фильтр авторизации, роли доступа.

## Аутентификация и авторизация

Аутентификация полностью **stateless**, построена на JWT:

* **Access-токен** — короткоживущий (по умолчанию 15 минут, `jwt.access-ttl`), передаётся в заголовке `Authorization: Bearer <token>` на каждый защищённый запрос, проверяется отдельным security-фильтром без обращения к БД.
* **Refresh-токен** — долгоживущий (по умолчанию 1 день, `jwt.refresh-ttl`), хранится в Redis (белый список активных токенов по `jti`), используется только для обновления пары токенов через `POST /auth/refreshToken`.
* **Ротация refresh-токена** — при каждом обновлении старый refresh-токен инвалидируется в Redis, выдаётся новая пара токенов; повторное использование уже потраченного refresh-токена отклоняется.
* **Отзыв (logout)** — `POST /auth/logout` удаляет `jti` refresh-токена из Redis; после этого токен больше не может быть использован для обновления.
* **Роли** — `ROLE_USER` / `ROLE_ADMIN`, разграничение доступа на уровне `SecurityConfig` (`hasRole(...)`) для `/cart/**`, `/orders/**`, `/admin/**`.

## Кэширование

Каталог товаров и список категорий кэшируются в Redis через Spring Cache (`@Cacheable` в `ProductService`), TTL задаётся `redis.cache-tll` (по умолчанию 20 минут). При обновлении или удалении товара кэш инвалидируется точечно по ключу (`@CacheEvict` в `AdminService`). Сериализация — типизированный JSON-сериализатор (без reflection-based Java-сериализации). Нагрузочное тестирование подтвердило снижение среднего времени ответа и рост пропускной способности при прогретом кэше (см. метрики ниже).

## Rate limiting

Все запросы проходят через `RateLimiterFilter`, который считает попадания в Redis (`INCR` + `EXPIRE`) по окну фиксированной длины в 1 минуту. Клиент определяется по заголовку `X-API-KEY`, а если он не передан — по IP-адресу запроса. Лимит — 10 запросов в минуту на клиента; при превышении сервер отвечает `429 Too Many Requests`.

## Автоматическая отмена заказа

При создании заказ получает статус `CREATED` и время истечения `expires_at` (+30 минут от момента создания). Раз в минуту `OrderExpirationScheduler` находит просроченные неоплаченные заказы (по индексу `idx_orders_status_expires_at`), возвращает зарезервированный товар на склад и переводит заказ в статус `CANCELED`. Конфликт с параллельной оплатой того же заказа перехватывается за счёт `@Version`-блокировки — при `OptimisticLockException` конкретный заказ пропускается без прерывания обработки остальных.

## Реализованный функционал

* регистрация пользователей;
* JWT-аутентификация с access/refresh токенами, ротацией и отзывом;
* разграничение прав доступа по ролям (`ROLE_USER` / `ROLE_ADMIN`);
* rate limiting запросов через Redis;
* просмотр каталога товаров с пагинацией и фильтрацией по категории;
* кэширование каталога и категорий через Redis;
* корзина: добавление, уменьшение и удаление позиций, очистка;
* создание заказа из корзины с резервированием товара на складе;
* автоматическая отмена неоплаченных заказов по таймауту с возвратом товара на склад;
* оплата заказа (условная — без интеграции с реальным платёжным провайдером);
* админ-панель: управление товарами (создание/обновление/удаление) и категориями (создание, переименование, список), повышение пользователя до администратора;
* обработка ошибок через Global Exception Handler;
* безопасное хранение паролей с использованием BCrypt;
* миграции схемы БД через Liquibase.

## Тестирование

Проект покрыт тестами на нескольких уровнях:

* **Модульные тесты сервисов** (`ServicesTest`) — бизнес-логика изолированно от Spring-контекста, с моками репозиториев (JUnit 5 + Mockito).
* **Тесты репозиториев** (`RepositoriesTest`) — `@DataJpaTest` поверх настоящего PostgreSQL в Testcontainers, проверяют JPQL-запросы и маппинг сущностей.
* **Интеграционные тесты** (`IntegrationTests`) — полный `@SpringBootTest` с Testcontainers, включая проверку конкурентного доступа к корзине.
* **Тесты контроллеров** (`ControllersTest`) — `MockMvc` поверх реальной `SecurityConfig`/`JwtFilter` с замоканными `JwtService`/`UserDetailService`/`RateLimiter`, проверяют HTTP-слой и авторизацию.

## Запуск проекта

### 1. Клонировать репозиторий

```bash
git clone https://github.com/samarityanin-hq/onlineStore.git
```

### 2. Запустить PostgreSQL и Redis

```bash
docker compose up -d
```

### 3. Запустить приложение

Запустите класс `OnlineStoreApplication` из IntelliJ IDEA либо через Gradle:

```bash
./gradlew bootRun
```

## Документация API

После запуска приложения Swagger доступен по адресу:

http://localhost:8080/swagger-ui/index.html#/

Через Swagger можно:

* просматривать все REST-эндпоинты;
* тестировать запросы (включая JWT — кнопка Authorize, токен из `POST /auth/login`);
* смотреть модели запросов и ответов.

## Postman

Для удобства тестирования проекта в репозитории находится коллекция Postman.

Импортируйте файл коллекции в Postman и выполните запросы. Для защищённых эндпоинтов сначала выполните `POST /auth/login`, полученный `token` подставьте в заголовок `Authorization: Bearer <token>` (или в переменную коллекции, если она настроена).

## Планы по развитию

* Circuit breaker (Resilience4j) на обращения к Redis — graceful degradation при недоступности кэша;
* Роль менеджера с доступом к управлению заказами (отдельно от полного доступа администратора);
* Вынесение сервиса доставки в отдельный микросервис (события через RabbitMQ + gRPC-стрим для приложения курьера);
* CI/CD (сборка → тесты → Docker-образ);
* Actuator + метрики (Prometheus/Micrometer).
