# Онлайн магазин

REST API интернет-магазина, разработанное на **Java** с использованием **Spring Boot**. Проект реализует JWT-аутентификацию (access + refresh токены с ротацией и отзывом через Redis), управление товарами, категориями и заказами, кэширование каталога через Redis, а также предоставляет REST API для взаимодействия с клиентскими приложениями.

> CSRF-защита отключена — при переходе на JWT (stateless-аутентификация без cookie-сессий) она неприменима: аутентификация идёт через заголовок `Authorization: Bearer`, а не через cookie, поэтому CSRF-атаки в этой схеме структурно невозможны.

## Архитектура проекта

Проект построен с использованием многослойной архитектуры.

```text
Client
   │
REST Controller
   │
Service ──── Redis (кэш каталога, refresh-токены)
   │
Repository
   │
PostgreSQL (миграции — Liquibase)
```

Основные слои:

* **Controller** — обработка HTTP-запросов;
* **Service** — бизнес-логика;
* **Repository** — взаимодействие с базой данных;
* **Entity** — модели базы данных;
* **DTO** — объекты передачи данных между клиентом и сервером;
* **Security** — JWT-аутентификация, фильтр авторизации, роли доступа.

## Аутентификация и авторизация

Аутентификация полностью **stateless**, построена на JWT:

* **Access-токен** — короткоживущий, передаётся в заголовке `Authorization: Bearer <token>` на каждый защищённый запрос, проверяется отдельным security-фильтром без обращения к БД.
* **Refresh-токен** — долгоживущий, хранится в Redis (белый список активных токенов по `jti`), используется только для обновления пары токенов через `POST /auth/refreshToken`.
* **Ротация refresh-токена** — при каждом обновлении старый refresh-токен инвалидируется в Redis, выдаётся новая пара токенов; повторное использование уже потраченного refresh-токена отклоняется.
* **Отзыв (logout)** — `POST /auth/logout` удаляет `jti` refresh-токена из Redis; после этого токен больше не может быть использован для обновления.
* **Роли** — `ROLE_USER` / `ROLE_ADMIN`, разграничение доступа на уровне `SecurityConfig` (`hasRole(...)`) для `/cart/**`, `/orders/**`, `/admin/**`.

## Кэширование

Каталог товаров кэшируется в Redis через Spring Cache (`@Cacheable`/`@CacheEvict`), сериализация — типизированный JSON-сериализатор (без reflection-based Java-сериализации). Нагрузочное тестирование подтвердило снижение среднего времени ответа и рост пропускной способности при прогретом кэше (см. метрики ниже).

## Реализованный функционал

* регистрация пользователей;
* JWT-аутентификация с access/refresh токенами, ротацией и отзывом;
* разграничение прав доступа по ролям;
* работа с товарами и категориями;
* кэширование каталога через Redis;
* создание и управление заказами;
* обработка ошибок через Global Exception Handler;
* безопасное хранение паролей с использованием BCrypt;
* миграции схемы БД через Liquibase.

## Запуск проекта

### 1. Клонировать репозиторий

```bash
git clone https://github.com/USERNAME/onlineStore.git
```

### 2. Запустить PostgreSQL и Redis

```bash
docker compose up -d
```

### 3. Запустить приложение

Запустите класс `OnlineStoreApplication` из IntelliJ IDEA либо через Gradle:

```bash
./gradlew bootRun
```

## Документация API

После запуска приложения Swagger доступен по адресу:

http://localhost:8080/swagger-ui/index.html#/

Через Swagger можно:

* просматривать все REST-эндпоинты;
* тестировать запросы (включая JWT — кнопка Authorize, токен из `POST /auth/login`);
* смотреть модели запросов и ответов.

## Postman

Для удобства тестирования проекта в репозитории находится коллекция Postman.

Импортируйте файл коллекции в Postman и выполните запросы. Для защищённых эндпоинтов сначала выполните `POST /auth/login`, полученный `token` подставьте в заголовок `Authorization: Bearer <token>` (или в переменную коллекции, если она настроена).

## Планы по развитию

* Устранить гонку при конкурентном списании остатка товара (optimistic locking / атомарный UPDATE) и при повторной оплате заказа;
* Rate limiting через Redis (`INCR` + `EXPIRE`) на публичные эндпоинты;
* Circuit breaker (Resilience4j) на обращения к Redis — graceful degradation при недоступности кэша;
* Расширенное нагрузочное тестирование `POST /orders` после исправления конкурентного доступа;
* Переход на модульную структуру монолита (package-by-feature: catalog / orders / cart / users);
* Роль менеджера с доступом к управлению заказами (отдельно от полного доступа администратора);
* Вынесение сервиса доставки в отдельный микросервис (события через RabbitMQ + gRPC-стрим для приложения курьера);
* Testcontainers для интеграционных тестов;
* CI/CD (сборка → тесты → Docker-образ);
* Actuator + метрики (Prometheus/Micrometer).
